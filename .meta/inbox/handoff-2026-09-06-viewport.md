## The specimen

- **Live artifact:** https://claude.ai/code/artifact/90d07ad3-0977-45dc-9e01-c298d15a6fbb
- **Source:** `~/Development/gaming/wotr/.meta/dossier/muster-roll.html`
  (self-contained; `README.md` beside it documents the structure and the
  republish flow).
- **The pattern it implements:** `~/Development/.meta/WORKFLOW.md`, Design
  Work → *"Tune each panel to the moment it will be read"* (2026-09-05): one
  viewport ≈ one working-memory chunk, sections in the order the need arises,
  sparse-and-critical per panel, state that persists across tab-switches.

What the page does, technically: one tab per subject (a `role="tabpanel"`
section with a `data-key`), a sticky per-tab progress strip, checklists whose
state persists per viewer in `localStorage`, light and dark themes through
CSS tokens (bare `:root` light; `prefers-color-scheme` dark guarded by
`:root:not([data-theme="light"])`; an explicit `[data-theme]` override),
three Google Fonts with fallbacks, no libraries, no build step. ~70 KB.

## Requirements as understood (for the draft to confirm or cut)

1. **A local executable, npm-shippable**, run against a project directory:
   `philset view` (or a subcommand of the philset CLI) serves a page from
   `.meta/` — no cloud, no CSP constraints, so libraries and local fonts are
   fair.
2. **Tabs over related documents** — the viewer picks *which* five of a
   hundred: a small manifest (front-matter or a `viewport.yml`) names the
   docs and their order; a default view might be the accepted designs plus
   `in-progress.md`.
3. **Markdown rendered with real typographic hierarchy** — the muster-roll
   tokens and spacing, not the IDE preview: headings, tables that scroll in
   their own container, callouts for ⚠ items, monospace for stats.
4. **Reading-moment ordering is authored, not inferred** — the source doc's
   section order is the panel order; the viewer does not reorganize.
5. **Per-viewer state without editing the source** — task-list items
   (`- [ ]`) become persisted checkboxes; the selected tab is remembered.
6. **Read-only.** Editing stays in the IDE (the inline-annotation workflow).
   A "last regenerated / source path" footer keeps provenance visible.
7. Theme-aware (system / light / dark) as the specimen is.

## Open design questions (for the draft, not decided here)

- Static generator (write an HTML file next to the docs, open it) vs a tiny
  server with live reload on `.meta/` changes. The specimen is static and was
  regenerated by hand each round; live reload is the obvious upgrade.
- Whether a doc declares its own panel structure (front-matter) or the
  viewer derives panels from H2s.
- Whether checklists write back to the markdown (probably not — read-only
  wins) or stay viewer-side.
- Relationship to `/hello`'s state read and to the artifact publish flow:
  the same source could feed both a local viewer and a published artifact.
